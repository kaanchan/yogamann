# Baseline Assessment (OpenPose + SDXL ControlNet)  
The current pipeline uses OpenPose for 2D keypoints and an SDXL-controlnet to render a wooden mannequin. In practice **OpenPose** works well on standard, upright poses, but it has known weaknesses with extreme or occluded poses. For example, users report that the SDXL+OpenPose control often “may not match your reference exactly” and frequently misses details like head/face angle【39†L137-L142】. OpenPose provides only the basic 25-body-joint skeleton (no finger/face details unless using separate modules), so it lacks fine-grained articulation. On the rendering side, SDXL produces generally realistic images, but it can hallucinate anatomy or style artifacts. Community tests find that SDXL’s pose control is *weaker* than SD1.5’s: e.g. an SDXL OpenPose control is “poorly trained” and cannot enforce the input skeleton as faithfully as older models【60†L158-L166】. In short, the baseline pipeline is stable and easy to run, but it fails to lock the output pose tightly to the input skeleton (especially for inversions or unusual angles) and it lacks detail (no face/hands). Its strengths are robustness and existing integration, but its key failure modes are pose drift and missing joints under extreme yoga poses【39†L137-L142】.

## Top 3 Pose Analyzers  

**Sapiens (Meta)** – Sapiens is a family of large vision transformers trained on 300M+ images that natively outputs 2D pose, segmentation, depth, etc. It was evaluated on *whole-body* pose benchmarks with far more keypoints (up to 308). In practice Sapiens far outperforms prior models. For example, a 0.6B Sapiens model achieves ~56.2 AP on the Humans-5K whole-body test, **beating** DWPose (53.1 AP) by about 3 points【13†L424-L432】. Meta reports Sapiens scales well (2B-model hits ~61.1 AP) and generalizes to “in-the-wild” and unseen poses【10†L32-L39】【13†L424-L432】. In concrete terms, Sapiens detects body, hands, face, and foot keypoints with high accuracy. Its output is compatible with downstream (it returns full keypoint sets and confidences via HF). The main weakness is resource usage: these are very large transformer models. The 0.6B model will still consume several GB of VRAM and has slower inference than lightweight nets (though 60s/image is permissible). Integration is a bit more complex (requires Meta’s Sapiens library), and on 16 GB it’s borderline to run multiple models simultaneously.  

**DWPose (Idea-Research)** – DWPose (“Deep-Whole-Body Pose Estimation”) is a two-stage MMPose model specifically designed for full-body (body+face+hands+feet) keypoints. It achieves state-of-art accuracy on whole-body benchmarks. For example, DWPose-large scores ~53.1 AP on COCO-WholeBody【13†L424-L432】. Unlike earlier single-stage models, DWPose explicitly distills whole-body knowledge, so it returns up to 18 body joints, 68 face landmarks, and 21 hand joints each. This high **keypoint coverage** is a big plus for downstream comparison. Community usage (via lllyasviel’s Annotators) shows DWPose gives robust skeletons even in unusual poses. It’s also relatively efficient (the “-l” model is only ~4.5 GFLOPs). The downside: it still lags behind Sapiens in accuracy, and its training strategy (teacher-student distillation) is complex. Empirically it can miss very extreme articulations if the 2D detector fails, and it needs MMPose’s framework (requires installing that toolbox). In summary, DWPose is a strong whole-body pose detector with wide keypoint coverage, but its main weakness is that it’s superseded by newer models in accuracy and can be heavier to deploy in a pure Python pipeline.  

**RTMPose (OpenMMLab)** – RTMPose is designed for real-time multi-person pose estimation with efficiency. Its m/s/l/x model series trades off speed vs accuracy. Notably, RTMPose-large achieves comparable whole-body accuracy (e.g. ~66.1 AP on COCO-WholeBody【56†L619-L623】, slightly above HRNet’s 65.3) while being much lighter (10 GFLOPs vs 35+ for HRNet). On standard COCO-body tasks, RTMPose-m hits 75.8% AP with >430 FPS on a GTX1660Ti【19†L17-L23】, showing how fast it is. The key advantages for our use case: it runs on a variety of hardware (CPU/GPU/mobile), and it’s easy to use via MMDeploy/ONNX. It outputs full body+foot keypoints in a single shot. In practice, RTMPose handles many poses quickly and can even be used in streaming. Weaknesses: its focus on speed means it has fewer keypoints (no face landmarks, fewer fine joints than Sapiens/DWPose), and its accuracy on very extreme poses is only moderate. In tests, the RTMPose-x model scores ~65.3% on COCO-WholeBody【19†L17-L23】, which is good but behind Sapiens. Also, it’s top-down (needs a person detector), so occlusions or multi-person may complicate processing. Overall, RTMPose is a solid, high-throughput option, but it trades off the finest detail and peak accuracy for speed.

## Top 3 Pose Renderers  

**FLUX.1-dev + ControlNet (Diffusion)** – FLUX.1-dev is a new diffusion model (by InstantX) that excels at rendering people and following pose instructions. In informal benchmarks it *significantly* outperforms SDXL on controlled poses: one test found that FLUX yielded a correct arm-raise pose nearly every time, while SDXL often flipped limbs【32†L121-L124】. FLUX also handles hands much better (producing coherent fingers instead of bizarre blobs)【32†L157-L161】. Paired with a specialized OpenPose ControlNet (or the union model), it can produce clean, photorealistic mannequins matching the input skeleton. Being diffusion-based, it is easy to integrate via diffusers/PyTorch and can run on our RTX 5080. Its VRAM use is moderate (Flux model is designed to run in ~16 GB). The key weakness is maturity: the FLUX ecosystem is very new and experimental. Official “union” control nets (for multi-control) exist, but they are still in beta and reportedly undertrained【21†L99-L102】. In practice one might need to tune strengths or ensembling for best fidelity. Also, as with any diffusion model, it can still produce subtle style artifacts or slight deviations in anatomy if weights are too high. But overall FLUX has proven far more pose-faithful than SDXL in tests【32†L121-L124】. 

**SMPL-X + Blender (Parametric)** – This is a classic 3D model pipeline. SMPL-X is a full 3D human mesh model (body+face+hands) that can be *fitted* to 2D keypoints. Tools like SMPLify-X perform an optimization: they adjust the 3D pose parameters so that the projected joints align with the detected keypoints【45†L39-L43】【50†L304-L312】. The result is an anatomically coherent 3D body in the exact input pose. We can then render this mesh (in Blender headless) with a neutral wooden shader to produce the final image. The big advantage: physics and body priors in SMPL prevent impossible angles (no limb interpenetration) and guarantee anatomical correctness【45†L39-L43】. In principle, this yields 100% reliable joint alignment (at least in the joints that were fitted). For yoga poses, the optimization will struggle less with hallucinated limbs because everything is constrained by the mesh. However, in practice such 2D-to-3D fitting is underdetermined: many 3D poses can produce the same 2D projection. Users of SMPLify-X note that arms or hands often still misalign even given perfect keypoints【51†L219-L227】. In extreme cases (inversions, self-occlusion) the solver might guess a plausible but incorrect depth, and the final 2D render could shift the pose subtly. Implementation is also more complex: it requires running an optimizer (possibly per image) and a 3D renderer pipeline. The primary weakness is thus **rigidity vs ambiguity**: SMPL methods enforce valid geometry but can misfit in the dark, and there is no straightforward “failure output” – it will always give some mesh, even if wrong (e.g. [51] shows arms not matching). Also, using Blender increases development overhead. In summary, SMPL+Blender would yield perfect anatomical poses when it works, but it often fails to capture fine articulations if the 2D input is noisy or ambiguous【51†L219-L227】.

**Stable Diffusion XL + ControlNet (Diffusion)** – SDXL is the current baseline diffusion model for pose rendering. It is capable of photorealistic output and supports ControlNet conditioning. In general it produces *high-quality* images with consistent style. However, multiple sources note that SDXL’s pose-control is surprisingly weak. As mentioned, users find that SDXL’s OpenPose control nets often “do not work as well as 1.5” and can “miss details like face angle”【39†L137-L142】【60†L158-L166】. In practice, SDXL might obey the skeleton roughly but still hallucinate limb positions or facial orientation. Its advantage is maturity: SDXL + ControlNet is well-documented and likely easier to implement (diffusers provide pretrained UNets and control nets). It also uses roughly similar VRAM as FLUX. The weakness is clear: fidelity to the exact pose is lower than with FLUX or a parametric approach, especially for subtle or uncommon joint configurations. In addition, some style artifacts (weird lighting, clothing) can slip through, which might confuse a VLM evaluator. Overall, SDXL+ControlNet is reliable and integrated but less trustworthy for precise alignment.  

*(Hybrid note: We did not find any ready-made “hybrid” system that fits a 3D model then refines with diffusion. Conceptually one could fit SMPL to validate or correct a pose and then use a diffusion model for texture, but no open-source pipeline implements this out of the box.)*

## Recommended Analyzer+Renderer Pairing  

For this yoga-alignment use case, we prioritize maximal pose accuracy and coverage. **Recommended:** use the Sapiens pose analyzer (e.g. the 0.6B model) together with the FLUX.1-dev ControlNet renderer. Sapiens delivers the most accurate and complete 2D skeleton (body+hands+face)【13†L424-L432】, which gives the VLM evaluator maximal information to compare. FLUX.1-dev has been shown to reproduce given poses far more faithfully than alternatives【32†L121-L124】, so the rendered mannequin will match the source pose with minimal hallucination. This combination yields the highest alignment fidelity: Sapiens will detect even subtle joints (like fingertips), and FLUX will preserve them in the output. The main downside is complexity and resource use – both components are large models – but on a 16 GB GPU with one-image-per-minute budgets, it is feasible. Compared to the baseline, this pairing should dramatically reduce pose errors. SMPL+Blender is a close alternative for strict geometric validity, but its tendency to misfit limbs (per【51†L219-L227】) and higher integration complexity make the Sapiens+FLUX approach preferable for our needs.
